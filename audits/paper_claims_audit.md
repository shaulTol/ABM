#### T1-ENT: Entropy values (Ĥ ± SE)

**Root cause investigation**: The plotting script (`plot_multiprompt_sweep.py` line 52) reads `d["entropy"]["knn"]["k5"]["50"]` from `gen_*_entropy.json` files. These kNN values are large negative numbers (e.g., person gs=1: -69.26, elderly gs=7.5: -104.72). The committed figure (`fig_sdxl_ssa_vs_entropy.png`) plots these raw negative values on the right y-axis (-60 to -90 range).

**Exhaustive search for matching convention** (person gs=1 kNN k=5 d=50 = -69.258):

| Transformation | Result | Match 5.68? |
|---|---|---|
| Raw kNN k=5 d=50 | -69.26 | No |
| -H/d (per-dimension) | 1.385 | No |
| H + (d/2)log(2πe) (excess over Gaussian) | 1.689 | No |
| H/ln(2) (bits) | -99.9 | No |
| Gaussian entropy d=50 (from same JSON) | -109.8 | No |
| KDE entropy d=2 | -0.874 | No |
| KDE entropy d=5 | -2.984 | No |
| All d ∈ {2,5,10,15,20,30,50} × all k ∈ {3,5,10} × {kNN, Gaussian, KDE} | all negative | No |

No transformation of any field in the committed entropy JSONs reproduces the paper's positive values. The literal strings "5.68" and "5.37" do not appear anywhere in the repository. Git history shows no convention changes in `plot_multiprompt_sweep.py` or `generate_and_entropy.py`.

**Conclusion**: The paper's entropy values were computed by a method or convention not present in the committed repository (possibly an Overleaf-only computation or an earlier uncommitted script).

**Entropy JSON files**: `experiments/sdxl/results_multiprompt_sweep/gen_mp_p*_entropy.json` (generated by `generate_and_entropy.py`). Each contains `entropy.{gaussian,knn,kde}` at multiple PCA dimensions — all values negative.

### Critical Deviations Requiring Attention

1. **Lag selection conditions (ii) and (iii) not implemented**: The paper presents a three-part criterion (eigenvalue floor + dip test + rho < 1/e) as the lag-selection rule. In code, only the eigenvalue floor is automated. The dip test runs post-hoc. The 1/e guard is never checked. This means the paper describes a stricter algorithm than what actually runs. **Risk**: A reviewer implementing the algorithm from the pseudocode would get different tau* values if the dip test or 1/e guard matters at certain lags.

2. **Autocovariance estimator mismatch**: Algorithm 1 line 7 writes the trajectory-averaged estimator `(1/(N(T+1-tau))) sum_{n,t}`, but the SDXL and synthetic spikes pipelines use the simpler single-pair estimator `(1/N) sum_n (X_tau - mu)(X_0 - mu)^T`. The trajectory-averaged form is more data-efficient (uses all overlapping pairs), while the single-pair form is more memory-efficient (no need to store full trajectories). Both are unbiased. The paper should note which estimator is used in each experiment, or the pseudocode should match the actual implementation.

3. **Eigenvalue sorting by absolute value vs by value**: `sdxl_components.py` sorts eigenvalues by `abs()`, which differs from the paper's "lambda_1 >= lambda_2 >= ..." ordering. For practical purposes the leading eigenvalue is always positive (metastable signal), so the result is identical, but the code could in principle rank a large negative eigenvalue (from noise) above a smaller positive signal eigenvalue.
